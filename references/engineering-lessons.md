# 工程复盘：从本地直播工具到可分发 skill

这份文档面向维护者，记录实现选择、封装时发现的问题、已经采取的措施，以及核心服务仍未解决的限制。具体操作命令见[环境安装](setup.md)、[故障排查](troubleshooting.md)和[发布指南](publishing.md)。本文依据仓库代码、封装过程中复现的 CLI 问题和离线测试整理，不使用用户录音或现场转写作为公开示例。

## 构建过程与设计取舍

原项目使用 FastAPI 管理监听任务：Playwright 打开页面，soundcard 回录默认扬声器，WAV 分段交给 FrameNotes 或 faster-whisper，随后更新转写和笔记。SSE 将任务快照推送给查看器。这个组合适合先打通本机链路，但依赖桌面、播放设备、网页状态和模型运行环境，不能仅按普通 HTTP 服务判断是否可用。

封装阶段保留了现有服务，增加三个层次：`SKILL.md` 规定 agent 如何操作和核对结果；`scripts/redbook.py` 提供稳定入口与常见误操作保护；`scripts/package_skill.py` 定义可分发内容和校验规则。参考文档分别解释安装、接口、排障和笔记质量，避免把维护细节全部塞进入口文件。

本次工作的目标是让项目能够被安装、正确调用和审阅。**封装可靠性、调用保护、录制能力是三件不同的事。** 下文分别列出“已在封装中修复”“仅由 CLI/skill 限制风险”“核心仍未解决”，防止把文档说明或客户端保护当成后端能力升级。

## 已在封装中修复的问题

| 触发场景与根因 | 本次处理与证据 | 验证方式及仍需注意的范围 |
| --- | --- | --- |
| 在干净 Windows 环境生成日期时可能找不到 `Asia/Shanghai`。`notes.py` 使用 `ZoneInfo`，原依赖未声明时区数据库；开发机已有数据会掩盖这个缺口。 | 在 `pyproject.toml` 增加 `tzdata`，doctor 检查该时区是否可加载。这是代码审查发现的安装缺口，不等同于记录了一次用户录制故障。 | 日期测试核对 UTC 到上海时间的转换；仍需使用实际运行解释器安装依赖。doctor 的结果不代表音频链路通过。 |
| API 测试使用 `FastAPI TestClient`，原开发依赖只有 pytest，干净环境缺少 httpx 时可能无法收集测试。 | 将 `httpx` 加入 dev 依赖；`requirements.txt` 引用统一项目声明，减少两份依赖清单漂移。 | 用 `pip install -e ".[dev]"` 安装后运行 API/viewer 测试；测试环境可复现性与真实声卡可用性分开验证。 |
| 原安装元数据缺少明确构建后端与源码发现配置；不同安装入口可能依赖工具的隐式行为。 | 声明 setuptools 构建后端、`src` 包发现、README 和仓库元数据；声明 Pydantic 2 及匹配的 FastAPI 下限，因为代码使用 `model_dump()`。 | 检查项目安装及导入、离线测试和构建输出。依赖尚未全面锁定版本，未来依赖升级仍可能影响行为。 |
| 把 skill 装到新目录后，从别处启动服务，原 `runtime/jobs` 会跟随进程当前目录，导致用户找错产物。 | CLI 根据自身文件定位 skill 根目录；serve 默认使用根目录下的 `runtime/jobs`。用户传入的相对 `--runtime-dir` 在改变工作目录前解析。 | 检查 `serve()` 的路径处理和启动时打印的数据位置；CLI 单元测试不覆盖实际服务启动。裸 uvicorn 仍保留原来相对工作目录的行为。 |
| 分享文本如“查看（https://xhslink.com/example），点击打开”没有空格，初版提取器只去掉末尾标点，把中文说明也拼进 URL。 | 正则在中文句读和括号处结束匹配；用解析后的 hostname 检查主域/子域，拒绝带账号信息的 URL，重复同一链接去重，多目标报错。 | `tests/test_skill_cli.py` 保留此复现案例，也核对查询参数、仿冒域名和多链接。它只做本地解析，不证明目标是直播或网页一定可播放。 |
| 导出滚动 note 会遗漏旧原文，因为正文只保留最近 80 条；直接重用输出目录又可能覆盖用户已有文件。 | export 使用 API 全部 segments 生成 `snapshot.json` 和 `transcript.md`，滚动 `note.md` 仅作为草稿附带；输出目录必须不存在。 | CLI 测试验证 125 条片段的顺序和原文、快照完整保留及已有目录不被改写。导出不复制音频，也不能找回服务未录到或未成功转写的内容。 |

链接解析修复只覆盖 CLI。原 API 接收 `HttpUrl`，原 viewer 仍有自己的正则；这次没有把所有入口统一到同一套链接处理逻辑。

## 发布包为什么需要独立边界

`.gitignore` 约束 Git 的未跟踪文件，不能约束普通 ZIP 工具，也不会让已跟踪的数据自动退出版本库。因此发布采用明确的路径和扩展名白名单：skill 入口、元数据、服务源码、脚本、参考文档、模板和依赖声明随包提供；运行目录、环境、录音、浏览器资料、测试和仓库基础设施不进入安装包。

| 容易踩到的坑 | 当前措施 | 验证与限制 |
| --- | --- | --- |
| 在开发目录中直接压缩，误收录录音、登录资料或模型文件。 | 打包器只读取允许路径，拒绝目录链接和符号链接，并限制文件与包的大小。 | 包测试放入虚构的私有标记文件，确认归档中不存在。白名单不能识别维护者手写进源码/文档的敏感内容，发布前仍要审阅 diff。 |
| 只复制 SKILL.md，或文档链接指向开发机路径、仓库中未随包提供的文件。 | 完整源码随包分发；验证入口元数据、文本编码、Python 语法及文档内的相对链接。 | 包测试在新目录解压后重新验证；测试与 CI 路径在文档中作为代码文字提及，避免链接到包外文件。完整包仍需安装 Python 依赖、Chromium 和实际使用的模型。 |
| 重新构建时覆盖正在审阅的产物，或两个构建进程争抢同一文件名。 | 默认拒绝同名 ZIP；先写临时文件并验证，再发布到目标路径。只有显式 `--force` 才替换指定 ZIP。脚本只清理自己那一个明确的临时文件。 | 包测试检查默认不覆盖、显式替换和相同输入的重复构建。默认发布使用同文件系统硬链接，目标文件系统必须支持该操作。 |
| 文件被改写但归档仍能正常打开，误以为内容可信。 | 内置 `MANIFEST.json` 记录每个文件的 SHA-256 和大小；校验归档条目、白名单及清单一致性。 | 测试验证文件改写、额外条目、危险路径和符号链接会被拒绝。散列清单用于发现内容不一致，不是发布者数字签名。 |

ZIP 读取当前工作区，Git 推送只包含已提交内容。两者若来自不同状态，就会出现“安装包有修复、仓库没有修复”的问题。发布时应先核对待发布源码，再从同一版本生成归档；不要仅凭 ZIP 校验通过就声称 GitHub 上已经是对应版本。

## 仅由 CLI 和 skill 限制风险的问题

这些措施改善日常调用，但底层 API 的相关行为没有被修复。

| 核心行为与触发条件 | 已增加的调用保护 | 证据、验证和保护范围 |
| --- | --- | --- |
| `JobManager.stop()` 无条件写入 stopping；对已结束任务再次停止会让状态停在 stopping。 | CLI 先 GET，只在既非终态也非 stopping 时发送一次 POST；skill 要求等待终态。 | CLI 测试确认 stopped、failed、stopping 均不发送 POST。GET 与 POST 间仍有状态竞争，裸 API/viewer 也可绕过保护；真正幂等需要后端修改。 |
| 多个任务同时播放时，每个任务都回录同一默认扬声器，录音彼此污染。 | create 检查近期任务；serve 固定单 worker，skill 要求一次一个音频任务。 | CLI 测试确认近期存在 starting/listening/stopping 任务时不创建。查询只覆盖最近 20 个任务且非原子操作，没有服务级锁，也没有声源隔离。 |
| `listening` 仅表示浏览器打开流程返回；播放器可能仍未发声。 | doctor 检查依赖和可选设备枚举；skill 要求核对第一段非空转写是否确属目标直播。 | doctor 明确不录音、不下载模型；Mock API 测试不能证明播放和回录成功。必须用真实链路确认，不能把状态名当作结果证据。 |
| 财经关键词触发固定摘要，部分替换还可能改变原句；草稿可以包含原文没有明确支持的结论。 | 将 refined_note 定义为待核对草稿；agent 从完整原始 segments 另写 final_note，保留数字、条件、出处和疑词。 | 现有笔记测试覆盖有限示例；质量规范要求逐条回溯原文。它没有移除硬编码规则，也没有实现自动事实核对。 |

另一个状态陷阱是导出的 `partial`：它表示导出时任务是否仍处于活动状态。`failed` 也属于终态，所以 `partial: false` 不代表完整录到了直播。判断交付范围必须同时读取 status、error、segments 和已知缺段情况。

## 核心服务仍未解决的问题

| 问题与代码根因 | 当前可行做法 | 尚未达到的能力 |
| --- | --- | --- |
| **识别期间漏录。** `jobs.py` 顺序等待 record_chunk 和 transcribe，上一段 ASR 完成后才录下一段。偏移仍按已完成段数乘段长计算。 | 说明时间戳是累计录音坐标；保留分段证据，不声称连续覆盖整场。缩短段长只能改变延迟，不能消除间隙。 | 独立持续采集、转写队列、处理积压控制及真实采集时间轴。 |
| **停止不立即生效。** stop 仅设置事件，当前录音线程和 ASR 不被取消；接口最多等 5 秒，状态还可能先于浏览器清理进入终态。 | 请求一次后观察状态，导出已完成内容，给当前步骤收尾时间。 | 可界定的停止延迟、统一资源清理、幂等终态转换与故障收尾。 |
| **重启后丢失任务索引。** jobs 字典仅在内存；磁盘未保存完整任务配置、统一时间基准和状态日志。 | 服务可用时导出快照；历史文件按后端和分段顺序整理，缺少元数据时标注不确定性。 | 持久化查询、崩溃恢复、明确恢复策略及可追溯的任务生命周期。 |
| **下播判断容易误判或漏判。** 页面前 5000 字出现“回放”“主播暂时离开”等关键词，或任意媒体 ended，就触发结束；静音、暂停本身不结束。 | 核对 ended_reason 与页面证据，按用户意图处理；不得把猜测写成已下播事实。 | 主播放器识别、连续确认、页面状态适配和误判后的恢复策略。 |
| **ASR 集成契约不完整。** FrameNotes 通过脚本存在与 powershell 可用选择，执行失败不回退；两个后端原始 JSON 的时间基准不同。 | 按文档检查外部脚本输出；优先使用 API 已统一的 segments；保留后端信息不足的历史片段标识。 | 显式后端配置、版本化输出协议、统一磁盘格式、失败分段重试及可观测的模型状态。 |
| **平台支持缺少实测矩阵。** 音频层只寻找默认扬声器对应 loopback；浏览器使用新 context，没有复用登录态。安装成功不能证明系统路由和网页播放可用。 | Windows 作为主要环境；macOS/Linux 明确要求设备验证，登录和验证码由用户完成。 | 已验证的系统/设备组合、设备选择、运行权限诊断和稳定的平台适配。 |
| **笔记生成和长任务数据管理仍是简化实现。** 全部 segments 留在内存，API/SSE 发送完整快照；静音提示可能覆盖滚动 note，异常时不保证生成精炼稿。 | 将 snapshot/分段 JSON 作为证据来源；滚动显示只作浏览，失败后交付明确标注范围的已有内容。 | 可分页查询、增量事件、稳定的最终化流程，以及独立于财经主题的摘要实现。 |

## 验证经验：断言通过不等于现场可用

当前验证分为三个层次。已有测试包括 API/viewer、日期与少量笔记规则、CLI 的请求保护和完整导出，以及发布包的边界与完整性；它们使用模拟快照和临时夹具，不访问用户运行数据。

| 层次 | 能证明什么 | 不能据此宣称什么 |
| --- | --- | --- |
| 离线测试与包验证 | 被覆盖的解析、状态保护、导出、元数据和分发规则符合断言。 | 已登录平台、已录到声音、ASR 准确、整场连续无漏段。 |
| doctor / doctor --audio | 当前解释器的静态依赖、时区、浏览器文件，以及可选的默认设备枚举情况。 | 模型必定可加载、设备音量正确、声音来自目标直播。 |
| 经授权的真实短段验证 | 指定环境的一次播放、WAV、ASR 和文件产出链路确实工作。 | 其他操作系统也通过，或长时间运行、掉线恢复和结束判断已被验证。 |

维护文档时应记录验证命令、环境和适用范围，而不是保留一个很快过时的“全部通过”数字。新增能力应配对应的失败场景测试；不要为了让 CI 变绿而把桌面、音频或模型能力写成未运行的成功结果。

## 后续优先级与验收方向

以下是尚未实现的改进建议，不是当前功能清单。

1. **先修采集与生命周期。** 将持续音频采集和 ASR 解耦；后端实现单任务互斥、幂等停止和统一收尾。验收应覆盖 ASR 比段长更慢、停止恰逢结束、采集异常和连续采样时间的完整性，明确积压时如何处理。
2. **再补持久化与统一数据协议。** 保存请求参数、实际后端、采集时间、分段状态和错误；统一两种 ASR 的磁盘时间语义。验收应包括重启后可查询已完成片段、避免重复偏移，以及清楚区分继续转写旧音频与重新开始录制。
3. **随后改进内容质量与环境覆盖。** 去掉会补写结论的领域规则，采用能回溯原文的整理方式；增加播放器结束信号和设备组合的实测记录。验收重点是数字、否定、条件保真，误判下播的处理，以及每个平台实际通过的链路范围。

封装暴露出的共同经验是：把运行假设写成明确的接口约定，用最小可复现案例验证边界，把“有文件”“有状态”“有正确内容”分开判断。这样后续迭代才能知道哪些问题已修复，哪些只是暂时避开，哪些仍需要改动核心架构。
